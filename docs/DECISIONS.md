# Decisions

One line of rationale each. Newest at the bottom. Prefix D-nnn. Domain decisions carry `TODO(verify)` where a statutory value is seeded from research rather than confirmed from a primary source; see `docs/RESEARCH.md`.

## Engineering

- D-001 Operating mode is autonomous: both checkpoints in brief section 13 are removed by the user's instruction; decisions are recorded here instead of asked.
- D-002 TypeScript stays on 5.9.x, not 6 or 7, because the brief specifies 5.x strict and typescript-eslint support for 7 is not yet settled.
- D-003 Playwright is pinned to 1.56.1 because the container ships Chromium build 1194 for that version; the config also accepts `PLAYWRIGHT_CHROMIUM_PATH` for other machines.
- D-004 Routing: one Next.js App Router page (`app/page.tsx` plus `app/[...slug]/page.tsx`) prerenders every known path (static routes plus seed IDs from `generateStaticParams`) and hands navigation to a client-side router built on `history.pushState`. Reason: under `output: 'export'`, Next's own `<Link>` fetches an RSC payload per path and hard-navigates to a 404 for any path not prerendered, which breaks runtime-created referrals and meetings; the client router keeps the same path shape and never fetches. Deep links to seed entities still work because they are prerendered.
- D-005 Seed data is generated at startup by a deterministic generator (seeded PRNG, fixed default seed) rather than shipped as committed JSON; `pnpm seed:export` writes JSON for inspection. Reason: no regeneration step to forget, and `generateStaticParams` uses the same generator at build time.
- D-006 Demo "now" is fixed at 2026-09-02 09:00 Europe/London so clocks and screenshots are reproducible; Settings offers the real clock.
- D-007 Tauri is the primary shell and its config, Rust source and capabilities are written for macOS and Windows; the Linux CI container has no WebKitGTK so the Tauri binary is not built here. Electron is the verified fallback and both shells load the same `apps/web/out`. Neither shell changes the default build target because the brief allows an Electron switch only when Tauri blocks the work, and it does not.
- D-008 Workspace packages export TypeScript source directly and are compiled by Next through `transpilePackages`; no per-package build step.
- D-009 Zod 4 is imported from `zod` (the v4 API is the default export in 4.x); `@hookform/resolvers` 5.x supports it.
- D-010 Tailwind 4 is used CSS-first with `@theme` in `apps/web/styles/tokens.css` and `@custom-variant` for `[data-theme]`; no `tailwind.config.js`.
- D-011 Persistence: store changes are written to `localStorage` under a versioned key in the browser and to `@tauri-apps/plugin-store` in the Tauri shell; "Reset demo data" clears both.
- D-012 Every screen accepts a `?state=` query (loading, empty, error, restricted, offline, stale) so Playwright and demos can reach designed states without mocking internals. It is a demo affordance and stays in production builds because the mockup is always a demo.

- D-013 TanStack Table stays on the 8.21 line rather than the 9.x rewrite: the v9 API (`useTable`, feature composition) is new and its docs were unreachable through the session proxy; 8.x is stable and maintained. Upgrade path noted in HANDOVER.
- D-014 ESLint stays on 9.39 because `eslint-plugin-jsx-a11y` 6.10 declares no support for ESLint 10; the flat configs use `reactHooks.configs.flat.recommended` and `jsxA11y.flatConfigs.recommended`.
- D-015 Print packs use dedicated `--color-print-*` tokens (pure black, white and a mid grey) so Stylelint's no-hex rule holds outside tokens.css while print stays black on white.
- D-016 Decorative hairlines (`line-1`, `line-2`) are exempt from the 3:1 component check; a dedicated `line-3` token at 3:1 is used for every input and control boundary. The contrast script enforces `line-3`.
- D-017 Screenshots are written to the repository `docs/SCREENSHOTS` from an absolute path in `tooling/playwright`, whatever the Playwright working directory.
- D-018 Next.js telemetry is disabled through `apps/web/.env` (`NEXT_TELEMETRY_DISABLED=1`) so no build or dev command phones home.

- D-019 Chronology visibility per view: single-agency shows the user's own agency events; integrated shows events with `integrated` visibility plus the user's own agency events; the pack view shows integrated events of moderate or high significance only. Restricted events show only to full-access members of the restricted process.
- D-020a Pattern lenses are pure functions in `packages/domain/src/chronology/lenses.ts`, each returning event ids, spans and a finding that always ends with the same "prompt, not a conclusion" sentence.
- D-020b The add-event schema rejects a fact whose title or detail contains opinion markers ("I think", "seems", "probably") and points the user to an analysis note; an analysis note must link at least one fact.
- D-020c Print packs paginate in JS (18 rows a page) because Chrome cannot render page counters in fixed running headers; each page carries the marking, reference, subject and page number.
- D-020d Connector pulls run through TanStack Query with the mock latency (200 to 1500 ms) visible; pulled events land in the inbox as pending and never in a chronology.
- D-020e Every Person record view writes a `read` audit entry and every chronology export writes an `export` entry; restricted reads use `read-restricted`.
- D-024 `TableWrap` renders a labelled, focusable region (`role="region"`, `aria-label`, `tabindex=0`) because wide tables scroll sideways and WCAG 2.1.1 needs a keyboard way to scroll them. Cost: one extra tab stop per table. Callers pass `label` where "Table" is not descriptive.
- D-025 Scenario seeders are ordered 01 to 08 in `SCENARIOS` and run before the bulk population, so scenario ids are stable and never collide with generated ids. Seeders may not edit `build.ts`; wiring is a separate step.
- D-026 Admin and Reports render with the context drawer column closed (`data-chrome='wide'`), because configuration and returns have no selection for the drawer to describe and the tables need the width. Chair mode uses the same mechanism with the rail collapsed too.
- D-027 `tokens.css` uses `@theme static` so every design token is emitted to `:root` whether or not a stylesheet references it. Tailwind 4 otherwise tree-shakes unused theme variables, and agency and print colours are applied through inline `var()` lookups, which silently fell back to `currentColor` (the MARAC report's health bar rendered as ink).
- D-028 Working-day clocks skip the national bank holidays and the council's own holidays; the two lists are separate configuration (`bankHolidays`, `councilHolidays`) and both are editable in Admin. The national list follows the gov.uk bank holidays feed (Scotland division) and is re-read yearly.
- D-029 A clock rule may count back from an anchor (`direction: 'before'`). For the CPPM notice rule the trigger instant is the meeting date, so the clock reads "due 5 days before the meeting" without a second date field.
- D-032 Electron is the demo build. Tauri stays fully configured as the target shell for macOS and Windows and is built on those platforms (amends the "Tauri primary" reading of D-007 for the demo only).
- D-033 Admin's default theme and density apply on a device that has no appearance preference of its own yet; once someone chooses in Settings, that choice wins.
- D-037 Scottish bank holidays are loaded from a committed copy of the gov.uk bank holidays feed (`packages/domain/src/config/bank-holidays.json`, Scotland division only) and refreshed with `pnpm holidays:sync`; the dates were verified against the feed on 03 Sep 2026, including the one-off 15 June 2026.
- D-038 `@playwright/test` is pinned to 1.62.1 (supersedes the 1.56 pin in D-003). The Linux build container cannot download its Chromium through the proxy, so the suite runs there against the preinstalled Chromium through `PLAYWRIGHT_CHROMIUM_PATH`; on macOS or Windows run `pnpm exec playwright install chromium` once. ESLint stays on 9.

## Design

- D-020 ink-3 darkened to `#6F6759`, risk-high to `#B4400F`, risk-medium to `#8A5306` so every text colour passes 4.5:1 on every paper step; see DESIGN.md section 2.
- D-021 Two agency colours added: regulator (OPG, MWC, Care Inspectorate) and fire and rescue, because scenarios 1, 5 and 7 need them and neither fits an existing agency.
- D-022 No avatars, initials circles or photos anywhere; identity is name, date of birth and reference. Safeguarding and design reasons in DESIGN.md section 9.
- D-023 Pills are reserved for process and stage; agencies use marks (glyph + colour + label).

## Domain

- D-040 The IRD label is configurable per local area; default "Inter-agency Referral Discussion (IRD)" per the 2021 national guidance.
- D-041 Clock rules live in `packages/domain/src/clocks/rules.ts`; every rule carries `source` and `confidence` from `docs/RESEARCH.md`. Rules marked Verify or Local are `TODO(verify)` in code and are shown in Admin with their confidence.
- D-042 Need-to-know defaults to deny; where the brief's matrices are silent, the more restrictive reading is used (for example a referrer receives an acknowledgement and outcome only, never detail).
- D-043 MARAC perpetrators and their associates, and MAPPA victims, are hard exclusions in the need-to-know rules: no detail level, not even presence, can be granted to them through the UI.
- D-044 MAPPA records are `restricted` classification; non-members see a RestrictedState with break-glass (reason required, 4 hour window, audited). Break-glass is not available for MARAC perpetrator-linked personas at all.
- D-045 Council officer eligibility under ASP s52 is configuration (`aspCouncilOfficerEligibility` in `packages/domain/src/config/default-config.ts`), seeded as registered social worker, or nurse or occupational therapist with the required post-qualifying training, per the Code of Practice; `TODO(verify)` against the local council rule.
- D-046 An unborn baby is modelled as a Person with `lifeStage: 'unborn'` and `expectedDeliveryDate`, linked to the mother by an `unborn-child-of` relationship, so pre-birth IRDs and CPPMs have a subject without inventing a birth date.
- D-030 The first review CPPM is 6 months from the initial CPPM per Appendix D, with no local override; a review brought forward on significant change is a meeting decision and does not change the clock. Three CP clocks were added on the product owner's values (notice 5 calendar days before the CPPM, core group escalation 3 calendar days, post-birth review 3 months advisory), each marked to verify.
- D-031 Break-glass requires a reason category from the configured list (`breakGlassReasons`) plus free text of at least 15 characters; the audit entry records both and the window (`breakGlassHours`) is Admin configuration.
- D-034 Four towns and the care home were renamed to names with no search footprint (Auchentorran, Portlennan, Dunlarrick, Craiglarrick, Whinbrae House); the checks and the rejected candidates are in `docs/RESEARCH.md` section 6. Ardvale and Clydeshore stay.
- D-035 MARAC perpetrator and MAPPA victim exclusions are keyed on case role, not person identity: each process carries a case-role register (`parties`, entries sourced from the referral, from relationship records via `partiesFromRoles`, or recorded by hand with a reason); `isExcludedParty` resolves the exclusion rows against that register and runs before membership or matrix rows in `accessFor`; `excludedUserIds` is gone; the victim and her children are never derived as associates.
- D-047 The DAQ that accompanies a MARAC referral and the MAPPA referral both ask "Is there anyone else who must not receive information about this case?" (`mustNotReceive`, shared entry schema in `packages/domain/src/forms/must-not-receive.ts`). Each answer becomes a manual case-role register entry keyed by a typed name: `casePartySchema` accepts `name` as a third form beside `personId` and `userId`, and `isExcludedParty` matches a candidate `name` against those entries case-insensitively after trimming. The parties offered are limited to the roles the exclusion rows name for that process (MARAC: perpetrator, family or associates; MAPPA: victims, employer, family or associates, public). A repeated name for the same party replaces the earlier entry rather than duplicating it. `accessFor` still checks platform users by id only; matching users by typed name is deliberately not done, because namesakes would lock out the wrong person.
- D-036 Appendix D of the 2021 national guidance, read live on 03 Sep 2026, sets the CP clocks: notice 5 calendar days before the CPPM (High), core group escalation within 3 calendar days of a significant change or concern within the plan (High), first core group within 15 working days (High), review of a pre-birth plan within 3 months of the pre-birth CPPM (High, deferrable on professional judgement after the birth), an inquorate CPPM reconvened within 10 working days (High), the CPPM record distributed within 10 working days (High). The 28 day initial CPPM clock follows a child protection investigation; the "concern being raised" framing belongs to the unborn baby row.
- D-039 Distributing a minute from the meeting workspace completes the process's record distribution clock, and the minutes pack shows the distribution deadline while it is running.
- D-058 The product does not stamp OFFICIAL on everything. Annex 2 of the MAPPA National Guidance is explicit that there is no requirement to explicitly mark routine Official information, and a product that marks every screen and every page trains people to ignore markings, which is the opposite of what the scheme is for. `marking()` returns undefined for Official and the print packs render nothing; only Official-Sensitive is marked, at the top and bottom of every printed page, in the page header on screen, on every share, and prefixed to a download's file name. Blanket marking is the common implementation mistake here and it is avoided deliberately.
- D-059 Classification is derived from the record, not chosen by whoever prints it. `classify()` in `packages/domain/src/classification` is pure and total: it takes what an artefact is about and returns a level with the Annex 2 example each decision rests on, so the Admin screen can show the rule table and the audit entry can cite it. A person may raise a classification with a recorded reason; lowering needs one of the configured roles (seeded as the Caldicott guardian and the MAPPA Coordinator) and is refused rather than applied quietly otherwise. A derived level is never lower than a linked record's, which is why the presence-only state exists. Handling instructions are local configuration, editable in Admin and marked to verify against the organisation's own information security policy, because descriptor practice varies and has changed across editions of the UK scheme. Secret and Top Secret are absent: nothing in scope reaches defence, diplomacy or national security, and the glossary says so rather than offering levels the product could never justify.
- D-057 The product is called Person360 and the hero screen is called the Person record. They cannot share a name: a user told to "open Person360" would not know whether that meant the application or one screen inside it, and a demonstration that says "this is Person360, and here is Person 360" invites the question rather than answering it. The route stays `/people/[id]` and the feature folder stays `features/person`, so nothing else moves; the screen's component and CSS module are `PersonRecord`, the captures are `person-record-*`, and the screen names itself in a kicker above the person's name. The product name lives in the catalogue as `product.name` and nothing hard-codes it, so a rebrand is one edit; the desktop shells read it from the same key as their menu text. The lantern glyph stands in for a wordmark until a mark is designed.
- D-055 A label copied word for word from a mandated return keeps that return's punctuation and capitalisation, em dashes included, and the em dash and casing checks make an exception for keys the context file flags `verbatim`. The brief forbids em dashes in the product's own voice; a statutory return's field labels are not the product's voice, and paraphrasing them would make a submitted return disagree with the template it is filling. The exception is keyed on the flag, so it never covers copy an author writes.
- D-056 A child protection register entry records concerns, not a category of registration. The 2021 national guidance says it is not necessary to identify a category when placing a child on the register, so concerns are the national construct, a child may carry more than one, and a local category is an optional free-text field for a partnership that uses one. De-registration reasons are the national statistics publication's nine coded reasons rather than free text, so the same list serves the register, the report and case closure.
- D-053 Domain vocabulary is display text, so it lives in `domain.*` keys and the enum values stay as identifiers: `agencyLabel`, `processShort`, `stageLabel`, `roleLabel`, `clockRuleLabel` and the rest in `@mas/domain` read the catalogue by id at call time, so an Admin override applies to a mark, a table and a print pack alike. The old `*_LABELS` records, `ROLE_DEFINITIONS[id].label` and the `label` and `trigger` fields on clock rules are gone from the schemas and the data. Enum values that used to be printed raw (a status shown as `in-progress` with the hyphen replaced) now have proper sentence-case labels, which is the one deliberate wording change of the migration. Access reasons are catalogue messages; register entries, audit labels and clock notes written into records at the time of an event stay as record data, like the seed.
- D-050 Every user-visible string lives in `packages/messages/src/en-GB.json` (ICU MessageFormat, nested by namespace, four levels at most, keys sorted) with `en-GB.context.json` describing where each one appears. Components render copy through `useT()` and non-React code through `t()`; both read one merged map built from three layers, the bundled catalogue, the local overrides file `en-GB.local.json`, and session overrides persisted only for the keys someone changed (localStorage in the browser, the Tauri store or the Electron app data directory in the shells). `pnpm messages:types` generates the `MessageKey` union and `MessageArgs` map from the JSON so a missing key or argument is a compile error; `pnpm messages:check` (part of `pnpm lint`) validates ICU syntax, key usage both ways, context coverage, sorting and the style rules; `pnpm messages:extract` lists literals still in source; a local ESLint rule (`mas/no-hardcoded-copy`) fails new hard-coded copy in every file that has migrated.
- D-051 `intl-messageformat` renders the catalogue directly rather than `next-intl` or `react-intl`. The app is a static export with its own client-side router and one locale: `next-intl` brings locale routing, middleware and server message loading the export cannot use, and `react-intl` adds an `IntlProvider` and component API around the same `intl-messageformat` engine without the runtime override layer the Admin editor needs. The catalogue is plain ICU JSON, so adopting either later means pointing its provider at `en-GB.json`, replacing `useT()` with its hook (the keys and messages do not change) and moving the override layer into its message loader.
- D-052 Dates and times are formatted with `Intl` for en-GB in Europe/London and passed into messages as arguments, never written into them. CLDR abbreviates September as "Sept" in en-GB, so `formatDate` in `@mas/messages` takes the day, month number and year from `Intl.DateTimeFormat.formatToParts` and supplies the three-letter month itself, keeping the brief's dd Mon yyyy exactly.
- D-049 Dates are typed, not picked: `DateField` in `packages/ui` takes text in dd Mon yyyy (also accepting 2 September 2026, 02/09/2026 and ISO), normalises it on blur, hands the form a yyyy-MM-dd calendar date and shows a format error with the example when the text is not a real date. Native `<input type="date">` renders in the browser's locale, which the product cannot control, so it is not used anywhere; the twelve date inputs (form dialogs, meeting due dates, admin holidays, the audit filter) all use the field. Every date field carries the format and an example as its hint; in a compact row (the audit filter, the meeting due and review dates, the admin holiday lists) the label carries the format instead, as "Due (dd Mon yyyy)", and the hint is suppressed so the row stays level.
- D-048 The MAPPA annual report carries Annex 3 Tables 1 to 9 of the MAPPA National Guidance for the year 1 April to 31 March, with the field set marked High on the product owner's instruction: Tables 1, 3, 4, 5, 6, 7 and 9 are computed from the record store, Table 2 from a civil order register added to the MAPPA detail (`orders`: SOPO, RSHO, FTO, SHPO, SRO or notification order, with made and expiry dates, court and status), and Table 8 (serious further offences) shows "Data not held" in every cell because the store holds no charge or conviction data. Figures that the store cannot supply (the rate per 100,000, wanted RSOs, breach convictions) also read "Data not held" rather than zero. The wording of every title and row is a placeholder in `apps/web/features/reports/mappaAnnex3.ts`, keyed by row id, so the supplied text replaces it in one file without touching the model.
- D-060 The workbook export refuses rather than overwrites. Every Total row of the ASP data workbook and its All adults column are SUM formulas, and a literal written on top of one leaves a workbook that looks right and stops adding up the moment anyone edits it: the failure that would go unnoticed longest. `nmdsCellMap` never emits a computed cell, `formulaCells` lists them so a test can prove it both ways, and `fillWorkbook` checks the template it was actually handed before writing each cell, returning what it skipped instead of throwing. A new edition of the workbook therefore surfaces as a visible list of refusals on the preview screen rather than as a silently broken return. The template is chosen from disk rather than bundled, because the workbook is published annually, the product makes no network calls, and a copy baked into the build would go stale without anyone noticing.
- D-061 The ASP field sets are the workbook's, not ours. Every list was reconstructed from the 2024-25 technical report's glossary until the 2026-27 workbook arrived; nine of them were wrong. Harm types were eleven and are twelve, because hoarding behaviour is its own type and self-neglect is qualified "excluding hoarding behaviour". Client groups were ten and are eleven, because infirmity or frailty due to age is a group in its own right and folding it into physical disability hides the largest single group in most areas' returns. The age bands were invented and are now the workbook's twelve. Location of harm was derived by pattern-matching the adult's address on the day, which is a guess, and a guess in a national return is worse than "Not known": it is now an eleven-value field on the concern. Referral source is its own field with the workbook's thirty-three values, because five NHS rows map to one agency and three map to no agency at all. The transcription lives in `workbook-2026-27.fields.json` as data rather than code, so the copy checkers leave the workbook's own punctuation alone and the next edition is a readable diff.
- D-062 A return that names a service under investigation is Official-Sensitive. Aggregate counts that name nobody are routine Official and carry no marking (D-058), which is what an ASP data workbook return usually is. Indicators 19b and 19c are the exception: they carry the Care Inspectorate CS number and the NHS hospital location code of every service under a Large Scale Investigation, which names a specific provider being investigated. So the classification is derived from the figures rather than fixed per report kind, and a quarter carrying any of those identifiers is prefixed OFFICIAL-SENSITIVE in the file name, before anyone opens it.


## Security and cryptography

- D-063 Primitives come from the @noble packages (`@noble/ciphers`, `@noble/curves`, `@noble/hashes`, `@noble/post-quantum`) and nothing in this repository implements one. They are audited, dependency-free and behave identically in WebKitGTK, WebView2, Chromium and Node, which is the deciding property: the product ships in two desktop shells and a browser, and a build that behaved differently under Tauri than under Electron would be untestable. WebCrypto alone was rejected for that reason and because it has no post-quantum primitives; it is still what supplies the CSPRNG. `tooling/no-weak-crypto.mjs` fails the build on MD5, SHA-1, ECB, DES, Triple DES, RC4, PBKDF2, scrypt, the platform pseudo-random source and any caller-supplied nonce, anywhere in the repository including for non-security purposes, because a reviewer grepping a safeguarding product for a broken hash will not stop to read what it was used for.
- D-064 One suite, named in every ciphertext: `v1-x25519-mlkem768-aes256gcm`. AES-256-GCM for content, with `seal` generating its own nonce and offering no way to supply one. Key establishment hybrid, X25519 and ML-KEM-768 both fed into HKDF-SHA-256, so the result holds if either half holds and an implementation flaw in the newer primitive is not fatal. Ed25519 for short-horizon signatures and ML-DSA-65 alongside it for anything that must verify in decades, because an audit entry or a meeting minute from 2026 may be read in a Learning Review in 2050. Argon2id for the recovery passphrase. One HKDF info string per purpose, so a key derived for the local store cannot be used as a blind index key. The AAD binds record id, classification and generation, length-prefixed so one field cannot impersonate another, which is what stops a ciphertext being moved from a routine record onto a restricted one. Decryption dispatches on the suite identifier it finds rather than the one the code prefers, `rewrapToSuite` makes a suite change a supported operation, and a fixture sealed on 03 Sep 2026 is opened by a test on every run and never regenerated.
- D-065 "Ensure that everything is end-to-end encrypted" is not implementable here and is not quietly reinterpreted either. The design encrypts every record to exactly the set of people entitled to see it, rather than encrypting everything to one organisational key, and says so in the product and the documentation. Three reasons the literal reading fails: the controller must answer subject access requests, sheriff court orders and scrutiny functions, so a system whose operator genuinely cannot decrypt would not be deployable; the ICO's encryption guidance treats data made inaccessible by encryption as a likely failure of Article 32 and possibly a breach in itself, and in safeguarding a locked-out practitioner at three in the morning is a child protection incident rather than a service level; and encrypting everything to one key defends against a stolen backup and nothing else, when the breaches that actually happen here are the curious colleague, the unentitled agency and the administrator with standing access. `docs/THREAT-MODEL.md` states the claim exactly and `docs/SECURITY.md` section 10 is the rule that no screen may exceed it.
- D-066 Entitlement is a key, not a boolean. The resolver returns the list of principals a record is wrapped to instead of answering "may this user see this?", so the need-to-know matrix and decryptability are the same fact. `canSee` was deleted rather than deprecated; `accessRank` replaces it for ordering and display and carries a comment saying it must never gate content. The rule is enforced by a test that reads every `.ts` and `.tsx` in `apps/web` and `packages/domain`, strips comments and fails if anything calls `canRead(` or `canSee(`, because a rule this easy to break by accident needs a check rather than a convention. Principal identifiers are opaque and prefixed by kind, never names or staff numbers, since they are visible to the operator. Presence-level readers are deliberately not wrapped, because presence is metadata and wrapping them would hand them the content; escrow is always wrapped, because a record escrow cannot reach is a record the controller cannot produce on a sheriff's order.
- D-067 Audit is signed, not encrypted. It exists to be read by the people it polices, a Caldicott guardian, an APC lead officer, an inspector and, if it comes to it, the ICO, and encrypting it to them would be backwards. Each entry carries its predecessor's hash and the actor's signature, so an alteration breaks the entry's own signature and a removal breaks the following link; verification stops at the first break because everything after it is unverifiable and a cascade would bury the one that matters. Actor, action, target, classification and timestamp stay in the clear and only the free-text detail is encrypted, to a set of oversight roles, since that is the field where a practitioner might write about a third party. The Admin screen verifies a deliberately tampered copy as well as the real ledger: a verification screen that has only ever said "verified" proves nothing.
- D-068 Escrow is two of five over Shamir's Secret Sharing across GF(256), with the five holders seeded in five different organisations, and `escrowDecision` refuses two holders from the same organisation in code rather than in policy, because policy is not what runs at two in the morning. `gfMul` is a loop rather than a log table lookup, so no multiplication indexes a table with a secret. Every use records a purpose from a fixed list, a lawful basis and a written reason, is signed by both holders so neither can later say they were not there, and notifies the remaining three. Recovery from a lost passphrase goes through the same path with the recovery purpose rather than a quieter one. Two colluding holders can read anything; that is a governance control, not a cryptographic one, and it is stated without hedging in the threat model, in `docs/SECURITY.md` and on the screen itself. Raising the threshold trades against availability, which is the same trade as the offline grace period.
- D-069 Search is client-side over what the signed-in user can decrypt, and reports how many records it covered and how many it could not, because a search that quietly covers less than expected is worse than one that says so. A blind index (HMAC-SHA-256 under a client-held key) supports exact match on reference numbers and on dates of birth bucketed to the month, and nothing else: it reveals equality, so names are excluded entirely and the date is bucketed to blunt a frequency attack. Encrypted search is not solved here and no screen says it is. Rejected: a searchable symmetric encryption scheme with better leakage properties, because every one of them leaks something and naming the trade-off plainly is worth more to the buying side than a scheme nobody in the room can evaluate.
- D-070 Connector data is encrypted where it already is, not where it arrives. A gateway runs inside each agency's own network holding that agency's key: it pulls from EMIS Web, ECLIPSE, iVPD or SEEMIS, maps to the event taxonomy, encrypts and pushes ciphertext, and the source system's credentials never leave the agency. That second half is the part an NHS information governance lead cares about most, because the obstacle to these integrations is rarely the data flowing out, it is being asked to give a supplier a service account on a clinical system. In the mockup the boundary is structural rather than deployed: the mock adapters run gateway-side and a test asserts the mock API receives only ciphertext.
- D-071 The offline grace period is 72 hours, seeded and configurable, and the remaining validity is shown rather than left to expire without explanation. Wrapped keys are cached locally under the device key so a practitioner in a house with no signal can open the safety plan, which is the normal case in this work rather than the edge case. The cost is stated: a device stolen while unlocked keeps its cached cases until the period expires. Shortening it narrows that window and widens the chance of a lock-out at three in the morning, and there is no value that avoids both.
- D-072 "What the host can see" is a screen, not a paragraph in a policy. Every information governance conversation in this sector reaches "who at the supplier can see my patients' records", and the honest answer has always been a document. Both panels render from the same store, the left through `serverView` which reads only what a server must hold and the right through `openProcess` which needs a key that unwraps. It shows the real metadata in full, including the classification and the opaque identifiers of every key holder, because a version that showed only ciphertext would be a lie and the one person in the room who knows that is the one who needs convincing. `docs/CRYPTO-INVENTORY.md` is generated from the source and checked for drift in `pnpm lint` for the same reason: a hand-written inventory is wrong the first time somebody adds an algorithm, and the NCSC's migration timeline makes a discovery inventory the 2028 deliverable, which this product meets at first release rather than migrates to.

## Review round (03 Sep 2026)

- D-073 RESTRICTED is not a classification and is gone from the product. It was abolished on 2 April 2014, when the six-tier Government Protective Marking Scheme (Unclassified, Protect, Restricted, Confidential, Secret, Top Secret) was replaced by the three-level Government Security Classification scheme; Official absorbed everything up to and including it and there is no direct mapping between the two. Annex 2 of the MAPPA National Guidance, which this repository already quoted correctly, names three levels and no fourth. `ClassificationLevel` is now `official | secret | top-secret`. Secret and Top Secret are in the type and unreachable: nothing in public protection casework reaches defence, diplomacy or national security, so `classify()` never returns them and a test asserts it over every subject shape the function accepts. They are present rather than omitted because a reviewer in a police or health board information security role needs to see that the scheme is the real one and not a two-level invention, and a type that offered only Official would read as though the author had not met the scheme. The glossary carries the abolition as its own entry, because a document that still uses the word as a marking is working to a scheme that has been gone for over a decade and someone should be able to look that up.
- D-074 Classification and access restriction are two properties and are now two fields. The old enum put them on one scale, which could not say that a MAPPA record is Official-Sensitive **and** access restricted, that an ASP case conference minute can be Official-Sensitive and not restricted, or that an aggregate report is neither. `Classification` is `{ level, sensitive, handling }`, where `sensitive` is the Official-Sensitive marking (a marking on a subset of Official, not a fourth level), and `AccessRestriction` is `none | restricted` beside it. Every record that was `restricted` becomes Official-Sensitive with `accessRestriction: 'restricted'`, which is what those records always meant. The word restricted now appears in three unrelated senses in the codebase, so the glossary spells all three out and the enum comment names them: access to a record; a chronology event's visibility; and the flag on an audit entry recording a restricted read. `ChronologyEvent.visibility` and `AuditEntry.restricted` are correct in their own terms and were left alone.
- D-075 The area's handling configuration is keyed on a marking profile rather than on a classification. `official`, `official-sensitive` and `access-restricted` are the three combinations an area needs to say something different about, and naming the third for what it is stops the configuration reintroducing the conflation the split removed. `profileClassification` builds the preview for the Admin screen from the profile, and the screen says in as many words that a profile is not a classification.
- D-076 The additional authenticated data gained an encoding version rather than a regenerated fixture. Sealing binds the classification, so the split changed what that field means: v1 carried one value that conflated the classification with access restriction, v2 carries `level/sensitive/restriction`. The field layout did not change and the meaning did, which is exactly when a domain separator has to move, so `person360/v1/aad` became `person360/v2/aad` and `open` tries every known encoding newest first, as suite dispatch already accepts an older suite identifier. The committed fixture from 03 Sep 2026 is **not** regenerated: `suiteCompat.test.ts` now asserts that it fails under v2 and succeeds under v1, and that a record sealed today succeeds under v2. A compatibility fixture regenerated when it fails is a fixture that tests nothing.
- D-077 Every share carries the classification of what was shared, captured at the moment of the share rather than resolved from the source at render time. `SharingRecord`, `InformationRequest` and `LawfulBasisRecord` all hold a `Classification` and an `AccessRestriction`; `Process` had the field and nothing downstream of it did, which meant the requirement that every share carries its marking was true of the record and false of the share. Captured rather than resolved because the source can be raised afterwards and the record of the decision has to say what actually went out under what marking: that is what the recipient acted on and what an inspector will ask about. A test over the whole seed asserts that no share is weaker than its source, in classification or in access restriction, because a quiet downgrade is only visible once someone looks for it and by then the share has been read.
- D-078 A recipient whose role may not receive Official-Sensitive content sees the marking and the reason they are on the list, and not the content. Marking and reason rather than nothing at all: a recipient who can see that something exists and why they were told can ask for it through the proper route, where one who sees an empty screen telephones the social worker. The roles are configuration (`officialSensitiveWithheldFrom`), stated as an exclusion rather than a permission list because a permitted-roles list is wrong the first time a role is added and nobody extends it, and wrong in the direction that withholds information from someone who needs it. Seeded from the roles that in this product only ever receive presence-level information and marked `TODO(verify)` against the partnership's own information sharing agreement, which is what actually decides this.
- D-079 `Person.ethnicity` is deleted. It was populated, which made three documents and two returns wrong, but not in the way that looked most likely: the values were not ethnicities. The bulk generator wrote the name pool's `origin` into it, so every person given a Scottish-sounding name carried "scottish" and every person given a Polish one carried "polish". That is a protected characteristic inferred from a name, which is the thing safeguarding data governance exists to prevent, and one report was already computing a minority ethnic figure from it. So the resolution is deletion rather than reconciliation: the field is gone from the schema, the seed and the generated data model, the MARAC return reports minority ethnic victims as not recorded like the other characteristics it does not hold, the DPIA's Article 9 list no longer names racial or ethnic origin and says instead that the field is deliberately absent, and a test walks every person in the seed and fails if one carries the key. A dead field on the most sensitive entity in the product is how a protected characteristic gets populated later by somebody who does not know why it was empty. The name pool keeps its `origin`, because that is a generator concern and describes which list a name came from rather than a fact about a person.
- D-080 A raised or lowered classification is stored on the record as well as audited. The audit entry is the record of the act; `classificationOverride` is the current state, and it carries the direction, the reason, the author, the timestamp and the id of the audit entry that recorded it. Both, not one: a ledger cannot answer "what is this record's classification now" without being replayed, and a field cannot answer "who changed it and why" at all. The join means a reader looking at a raised marking can reach the entry. The audit entry is written first so the record can cite its id.
- D-081 One function decides a record's classification. `effectiveClassification(config, record)` returns the override where there is one and the derivation otherwise, along with both, and every screen, print pack and export reads it. That is the failure a derived-plus-override model invites and the reason to close it in code rather than in review: one screen showing the marking a person set and another showing the one the rules give, on the same record, with nothing to say which is right.
- D-082 Two refusals are enforced in `overrideDecision` rather than in the dialog's disabled state, because the disabled state is not what runs when somebody scripts a change. A lower needs one of the configured roles. And an override may never be weaker than the strongest classification of any record it links to: that is the inheritance rule that stops a person record being lowered while it is linked to a MAPPA case, and it is the reason the presence-only state exists at all. The linked-record refusal binds a named role too, so the Caldicott guardian cannot lower a record below its link either.
- D-083 The override lives on the process and not on a share. A share carries a classification captured at the moment it went out (D-077), and letting somebody override a snapshot would defeat the capture: the point of the field is that it says what was actually shared. Person records have no stored classification to override, because theirs is derived at render from what they link to, which is what makes the inheritance rule work.
- D-084 The exclusion register stays an exact match, and gains a warning layer beside it. `isExcludedParty` compares hand-recorded names case-insensitively after trimming, which is exact string matching on the mechanism that stops a MARAC perpetrator receiving information about the case: "Ryan Kerr" does not match "Ryan James Kerr", "R Kerr", "Kerr, Ryan" or a copy carrying a non-breaking space, and the failure is silent and towards inclusion. Making the match fuzzy was rejected: a fuzzy match that silently excludes the wrong person is its own failure, and the register is deliberately a list somebody wrote down. So a similarity check runs alongside it. Adding a recipient, an invitee, a distribution entry or a pre-meeting request whose name resembles a register entry blocks behind a confirmation that quotes the entry as written, the date it was recorded, the party role and the reason, because a warning that only says "this looks similar" gives a person nothing to decide with and they will click through it. Both answers are audited with the entry that matched, so a wrong call is traceable rather than invisible. The check runs in reverse too, when a register entry is recorded, because an exclusion often arrives after the sharing has started and nothing else in the product would notice. The threshold is 0.82, seeded to catch the four documented cases and leave unrelated names alone; a deployment should make it configuration. It is a prompt and not a guarantee, and the threat model and the handover both say so.
- D-085 Escrow refuses a holder who is themselves an excluded party on the record being opened, in code, with the same shape as the same-organisation refusal and the same audit entry. The scenario is remote, the check is cheap, and the case-role register already answers the question, so refusing costs nothing and closes it; leaving the holders to notice it about themselves closes nothing. A holder is matched by account, by person record or by name, because the register records people all three ways, and a share held by a role with nobody named against it cannot be checked at all, which the screen says rather than implying it was. Recovery carries the same check the other way round: rewrapping a user's keys would hand back everything they held, so `casesWithheldFromRecovery` names the cases they are an excluded party on and those are not restored. The exclusion outlived the device.
- D-086 The internal names stay. The repository is `mas-platform`, the workspace packages are `@mas/*`, the Rust crate is `mas-platform-desktop`, the session key in local storage is `mas.session` and the desktop menu channel is `mas-menu`. None of them is user-visible: renaming them touches every import in the repository, invalidates every saved session and every screenshot path, and buys a reviewer nothing they can see. What a council installs is `Person360`, which is what `productName`, `mainBinaryName`, `build.productName`, `artifactName` and the window title all say, with the bundle identifier `uk.person360.app` in both shells. Recorded here so the next person does not spend an afternoon on it and so the inconsistency reads as a decision rather than an oversight.
- D-087 The browser device key is a residual risk in its own right and is listed as one. `docs/SECURITY.md` section 2 already recorded that in a browser the device private key lives in `localStorage`, but it was absent from both places that exist so nobody has to read for the residual risks. It is now in the threat model's collected list, in the security document's, and in the DPIA's residual risk table, stated plainly: a browser has no equivalent of the OS keychain, so any cross-site scripting flaw in the application reads the key and with it every wrapped key cached on that device. That is a materially different risk from the keychain path rather than a smaller version of it, which makes the desktop shells the supported deployment and the browser build a development and demonstration build. The Security page in Help now says that in the product, in the words somebody would use, rather than leaving it in a table two documents away.
- D-088 The dialog centres itself explicitly, at class specificity, and a build step reads the compiled CSS to check it still does. Every modal in the product rendered pinned to the top left at every width, and nothing caught it: the dialogs opened, the backdrop painted, the widths were right and focus went where it should. The cause was not in this repository's CSS. Tailwind's preflight emits `*,::after,::before,::backdrop { margin: 0 }`, which zeroes the user agent's `dialog { margin: auto }`, and a native dialog centres by resolving `auto` margins against its two zero insets. So the fix is not a reset override but a positive statement of the geometry on the component itself, `position: fixed; inset: 0; margin: auto`, which a universal selector cannot outrank. `tooling/dialog-margin-guard.mjs` then reads `apps/web/out` after a build and fails if no rule sets all three together, or if any dialog-named selector sets a zero margin, because the failure was invisible to every test that existed and a source-level lint would not have seen it either: the source was never where the problem was.
- D-089 There is one dialog primitive and no local variants. Native `<dialog>` opened with `showModal()`, for the top layer, the backdrop, the platform focus trap and Escape, and three regions on a `minmax(0, 1fr)` grid capped at `100dvh` minus the inset, so a form taller than the viewport scrolls its body and keeps its footer on screen. `showModal()` does not lock the page behind, so the primitive does, counted rather than set, and paired with React's own effect cleanup rather than with the element's `close` event: a dialog can leave the page without ever firing one, and a page locked by an element that no longer exists cannot be scrolled again. A size scale of four, `sm` for confirmations, `md` for most forms, `lg` for statutory ones and `full`, replaces per-dialog widths. `ConfirmDialog` is the yes-or-no shape, destructive in tone by default and never in wording, because the caller supplies the verb.
- D-090 A long form's validation failures are summarised at the top of the dialog body and take focus. Per-field messages alone are not enough on a form taller than the viewport: the three-point test does not fit in 700px, so a keyboard user who submits and is refused has to scroll the body hunting for red with nothing telling them what to look for. `formErrorSummary` walks the react-hook-form error tree, which nests because the schemas do, and the summary is an `alert` that says what is wrong in one place. It replaces nothing: the per-field messages stay, because the summary says what and the field says where.
- D-091 The contact sheet embeds one image per capture instead of two. It carried each screenshot twice, a 420px thumbnail for the grid and a 1280px copy for the lightbox, and 420px of a 1440px capture is 29 percent of native: enough to recognise a screen you already know, not enough to read one you do not, so telling two similar captures apart meant opening both. Raising the thumbnail to a legible width on top of the second copy went past the 16 MB the page has to fit in. Measured rather than guessed: 720px thumbnails plus the 1280px copies came to 15.3 MB, and 800px came to 16.2 MB. Dropping the second encoding pays for the first. One 1280px image now serves the grid card, where the browser downsamples it to a 440px column and the text stays crisp, and the viewer, which reads it from the card's own element rather than from a JSON blob that would put every capture in the file twice again. The page fell from 12.6 MB to 10.9 MB in the process, so the gallery did not need splitting by phase.
- D-092 Four named layout modes, chosen by width in one module, applied through one attribute. The layout broke below 1440 for a single structural reason: the grid's column widths came from media queries in the stylesheet and the components' own states came from the appearance store, so the two could disagree and did. At 1100px the rail's track was 72px while the rail still rendered its expanded contents, which want 125px, so the labels were sliced down the middle rather than replaced by icons; the drawer had the mirror of it, holding 360px at an 800px viewport and leaving the record 368px. `wide`, `standard`, `compact` and `narrow` are written to `data-layout` on the document element by `apps/web/lib/layout.ts`, and the stylesheet carries no media query for layout at all: every track is a custom property redefined per mode. A breakpoint therefore cannot be changed in one place and missed in the other, because there is only one place. A boot script writes it before the first paint, as the theme's does, so a compact viewport does not paint the wide layout once and reflow.
- D-093 The rail's icon state below 1280 is not a preference. Above it, a person can collapse the rail by hand and that is persisted. Below it, the icon rail is the only thing that fits, so the toggle is not rendered rather than being rendered and ignored, and `RailContents` takes a `compact` flag that changes what is in the markup rather than only how wide it is: the labels leave the link's accessible name and return as a title, the badge moves to the corner of the icon, the brand becomes the glyph. Below 1024 both side columns leave the page entirely and return as panels reached from the top bar, which is what carries WCAG 2.2 1.4.10: a 1280px viewport at 400 percent zoom is a 320px one, and 72px of icon rail is a fifth of it.
- D-094 The overlay rail and the overlay drawer are the dialog primitive, not a second overlay implementation. Both needed the same four things from the platform, the top layer, focus trapped inside, Escape and the page behind held still, and all four already existed in `Dialog` with a regression suite behind them. So `Dialog` gained a `placement` of `inline-start` or `inline-end`, which replaces the centring margin rather than removing it: `margin-inline: auto 0` against two zero insets pushes the panel to the end edge and keeps the block margins at `auto`, so nothing about it reintroduces the zero margin the compiled-CSS guard exists to catch. The drawer's content is computed by one hook and rendered by both shapes, because a need-to-know answer that differed between the docked column and the panel would be a second implementation of the access rules.
- D-095 Panels respond to the record's width, not the window's. `.app-content` is a size container named `record`, and the layouts inside query it. The record is 872px at 1440 with both side columns, 952px at 1024 with one, and 1312px at 1920: the number that decides whether two columns fit is the record's and the window's does not predict it. This is also what fixed the process record at 400 percent zoom, where the two column layout was collapsing correctly and the single column was still 453px wide, because a grid item's `min-width` defaults to `auto` and the full-width row's min-content was setting the track for everything above it.
- D-096 Text may wrap or it may truncate visibly, and nothing else. Wrapping is the default and is required for anything carrying a sentence; a person record's staff safety alert is the case that decides it, because "do not visit alone" with the reason truncated is worse than the untruncated version being long. Truncation is for identifiers in tight rows and must show an ellipsis and keep the full string reachable in a `title` or an accessible name. The third thing, text sliced off with no ellipsis, is forbidden because it looks like the text ended there. `Pill` enforces its half in the primitive: capped at its container's width and ellipsised, because a pill wider than the thing it sits in is a design error at that spot rather than something the layout should absorb, and one on the process record was 453px inside a 320px column and took the page sideways with it. A pill that genuinely carries a sentence asks for `wrap` and grows downwards instead. The policy is asserted on five screens rather than described in a document nobody re-reads.
- D-097 A link the reader is not entitled to follow looks exactly like one they are. That is the whole point, and it is the opposite of what most systems do. A link that is styled differently, greyed out or absent when the reader has no access tells them something about the record before they have asked for it, and it leaves no audit entry because nothing happened: the reader learns "there is something here I cannot see" for free and without a record of having learned it. So `PersonLink` renders the same anchor either way, and following it lands on the presence-only state, which says a record exists, that this reader may not read it, and how to ask, and that read is audited. The difference between a system that refuses and a system that hides is that only the first can be inspected afterwards.
- D-098 An excluded party is never a link. Where a case is in scope and the exclusion register names the person for its type and stage, the name renders marked and not clickable, with the party role after it for a screen reader. A link would put a route into their record next to the sentence saying they must not be given one, which is an invitation misfiled as a convenience. The decision lives in `PersonLink` and reads the register, rather than each screen deciding for itself: the MARAC referral panel had been rendering the perpetrator as a link beside a "must not receive anything about this process" pill since it was written, and that is precisely the failure a rule enforced in one place prevents from recurring on the next screen somebody writes.
- D-099 Practitioners have a card, at `/practitioners/<id>`. Every field on it was already in the seed and none of them had a screen: a colleague appeared as a name beside a case role and nothing else, so "who is the MHO on this and can I ring them" was answered by scrolling a members list and then not answered at all. That is the wrong gap for a multi-agency product to have, because the other agency's worker is the person you actually need. The card's case list is filtered by the reader's own access rather than the practitioner's, and says how many cases it is not showing: a card that listed every case a colleague holds would be a way round need-to-know that took one click.
- D-100 Two lists, answering two different questions, and neither is persisted. The trail answers "how did I get here" as the path actually walked, most recent last, truncating rather than appending when a record already on it is revisited, because a loop is not a queue. Recently viewed answers "what was I working on", in view order, most recent first. Both are session state: a trail restored from local storage after a week claims a journey that did not happen, and a list of the people whose records this account opened is not something to leave on a shared council laptop for whoever signs in next. The consequence is deliberate and visible in the test: reloading the page empties both.
- D-101 A clock links to the rule that sets it, and the rule opens from the address rather than from an effect. "Why is this five working days" is the question a sceptical practitioner asks first, and the answer, the source and the confidence, is in the timescale rule's own dialog. `/admin/timescales?rule=<id>` opens it. The open rule is derived from the query rather than copied into state on mount: an effect that calls setState on arrival is a second render for no reason and makes the address and the screen disagree the moment anyone presses back.
- D-102 The person network's list is visible and its diagram is decorative. The list used to be visually hidden, an accessible alternative to an `img`-role SVG, which was correct as far as it went and meant that the one screen showing who is around a person offered no way to reach any of them: a name in an SVG `text` element cannot be a link, so a sighted reader who wanted the sister's record went back to search and typed it. Now everyone gets the same list of links and the SVG is `aria-hidden`, which is also less to maintain: one source of the names rather than two.
- D-103 The process record says who the case is about, as against who is working it. The two were conflated: the participants panel lists practitioners, and the people the case actually concerns were visible only inside the drawer's need-to-know section, so a reader looking at a MARAC record could not see the perpetrator's name without opening a panel about something else. The case-party register now has its own panel, every name a link except the excluded ones, which is also what makes D-098 reachable rather than theoretical.
- D-104 The sign-in screen is one surface, and the honest statement is the second thing on it. The screen it replaces was two panes that stopped: a paper-coloured left half ending at 597px with four hundred pixels of nothing in it, and a bare right half carrying thirteen equal organisation cards. `docs/NOTES.md` has the full critique, written before the rebuild, because a rebuild without a written account of what was wrong is a redecoration. The rebuilt screen puts the masthead across the window with its contents on the body's own column so there is one left edge, and moves "this is a demonstration, every person, case, address, postcode and number in it is invented" from a footnote in the least looked at corner to a marked block immediately under the headline. It is the truest thing the screen has to say and it was set in the smallest type in the worst place.
- D-105 One field filters organisations and people together, and it takes focus on arrival. The screen's whole job is choosing who you are, so the fastest route in should be to type a name: "moira" narrows the organisation list to the Health and Social Care Partnership, selects it, and leaves Moira Gilmour as the only person on the right. Two lists behind one field rather than a search on each, because the reader does not know or care which of the two their word belongs to. Focusing an input on arrival is usually rude and is right here, because there is nothing else on the screen to read first.
- D-106 Both questions are visible at once, and the organisation is a list rather than a grid of cards. Thirteen equal cards across two thirds of the screen made the least interesting decision anybody makes here the largest one, and answering it pushed the persona list below the fold at 900px, which on a projector is a scroll in the first ten seconds. A single column list of thirteen costs 20rem and leaves the people the room they need. The chosen organisation is derived rather than held in state where the filter has removed it from the list, so there is never a frame where the two columns disagree, and no setState on arrival.
- D-107 The persona used last time is offered before either question is asked. `mas.lastPersona` was already written on sign-in and read on arrival, and the tag it drove appeared only after the organisation had been chosen, so the one person who most wants to get straight in, the person demonstrating this for the fourth time, still made both choices. It is now a card at the top with a Continue button. Still no credential field: a password box that accepts anything is a lie told in the first five seconds of a demonstration about honesty in information sharing, and there is nothing here to authenticate against.
- D-108 The demo clock is settable, and one instant drives everything. It was a fixed constant with a live toggle beside it, which meant the clocks were the part of the product hardest to show standing still: "the inquiry decision is due in three days" is a number on a screen, where moving the clock four days and watching the same clock go overdue, its band turn red, the worklist reorder and the home count change is the demonstration, and it is the thing a room of practitioners will actually test against what they know. `session.nowIso` holds it, `useNow()` is the only reader, and every statutory clock, countdown and relative date is computed from it. Moves are absolute rather than accumulated, so a jump forward and a jump back are the same operation and repeated moves cannot drift; setting it turns the live clock off, because a demo instant the real clock overwrites a second later is not a setting. An unparseable value is refused by the store rather than silently taken, and `parseDemoNow` still falls back to the seeded instant rather than returning an Invalid Date, because a screen full of "NaN days remaining" is a worse failure than a clock that did not move.
- D-109 The Playwright sign-in helper seeds a session only when there is not one already. It wrote `mas.session` unconditionally on every navigation, which quietly overwrote everything the application had put in the session since: a persona switched mid-test came back on the next `goto`, and the demo clock returned to the seeded instant the moment a test navigated after moving it. That is also what a person does: sign in once and keep the session until they change it. The bug was invisible until something other than the user id started living in the session, which is the usual shape of a test helper that is a little too helpful.
- D-110 One write pipeline, and the consequences of a write live in it rather than at each call site. `docs/FUNCTIONALITY-AUDIT.md` counted twenty-nine places that mutated the store and forty-seven that wrote an audit entry, with no rule connecting the two. That is how a product grows a fifteenth create path that forgets to start a clock, and the failure is silent: the record is there, the screen looks right, and the statutory deadline nobody is counting arrives anyway. `store.write()` runs the ten steps of `docs/RECORDS.md` section 7 in order. A caller says what it is writing and why; the pipeline decides what else must happen.
- D-111 Refusals are total and come before anything is written. The schema, the business rules the schema cannot express, the reason a change after the fact has to carry, the classification downgrade check and the exclusion register are all evaluated before the record reaches the store, so a refused write leaves no half-record, no orphan audit entry and no clock counting down against something that does not exist. Everything the pipeline then does is collected into the result rather than being invisible, so a screen can tell the practitioner what happened, "one clock started, one chronology event written, three people now entitled to read this", instead of each screen having to know in advance.
- D-112 The caller says what kind of chronology event it is; the pipeline decides whether one is written. An address move is `move.address` and a household change is `household.change`, and a pipeline that guessed would file every write under one taxonomy entry. What it enforces is the part that gets forgotten: that the event exists at all, with the right author, agency, instant and process links, and only where the change is a significant one. The significant-event list is in `docs/RECORDS.md` so the distinction is a decision rather than an accident.
- D-113 Step 9, the outbound connector proposal, is a seam in this commit rather than an outbox. The pipeline takes the proposals and reports them, and the outbox with its delivery state, its origin stamp, its idempotency key and its human authorisation is step 14, which is where the honest per-connector capability matrix lives too. Recorded here rather than discovered at fifteen call sites when step 14 lands: the shape the callers pass is fixed now, so adding the outbox behind it changes one function.
