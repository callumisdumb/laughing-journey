# Notes

Running log of what was tried visually, what was rejected and why. Newest at the bottom. Future passes read this before changing anything.

## Phase 0

- Wrote the design plan before code. First sketch of Home used three KPI tiles; rejected as generic (see DESIGN.md section 9). Replaced by typographic clocks.
- Considered a soft drop shadow on panels to lift them off the cream. Rejected: on paper-1 over paper-0 the shadow reads as grey smudge and the product starts looking like a marketing card grid. Hairline rules and paper steps do the job.
- Considered Beam's near-black chocolate `#2e1616` as the ink. Rejected: it pulls red and fights the risk colours. Our ink `#22201B` is a warm olive-black that sits neutrally next to red, amber and green.
- Considered using the agency colour as the left border of chronology rows (a common pattern). Rejected in favour of glyph + colour + label inside the agency cell, because a coloured border alone is colour-only meaning and looks like a Kanban.
- Contrast arithmetic on the brief's starting tokens showed ink-3, risk-high and risk-medium failing on paper-2. Adjusted before writing any CSS so the checker is green from the first build.

## Phase 1

- First screenshots at 1280 by 720 (the Playwright device preset overrode the 1440 by 900 viewport). The top bar search collapsed to 130px because a flex spacer competed with it. Fixed both: device preset spread first, spacer removed, search grows with a 160px minimum.
- The clocks chip read "0 clocks due" for Janet, whose only clock is 12 days out. Changed the copy to "No clocks due this week" so zero reads as reassurance, not an error.

Considered a full-bleed photograph or illustration. Rejected: the product has no imagery language and a stock image would make it look like a marketing site.

- Keyboard walk: rail, search, clocks chip, notifications, persona switcher, worklist rows and the drawer toggle are all reachable in order with a visible heather focus ring. Persona switcher is a native dialog so Escape and focus trapping come free.

## Phase 2

### What was tried and rejected

- Person record header: tried a two-row header with the process badges under the name. Rejected: the badges belong at the right, where the eye goes for "what is happening now", and the name row stays clean. The cover-sheet rule under the header (2px ink) is the only heavy line on the page and it works.
- Network graph: the first pass used 11px labels in a 520-unit viewBox. At the rendered size they were unreadable and the left-hand label clipped. Enlarged the viewBox to 640 by 360, labels to 0.9375rem and pulled the rings inward. No initials circles (D-022); a small filled marker for the subject, paper-2 fill for household members, dashed stroke for an adult of concern.
- Lanes chart: tried colouring the points by significance. Rejected: colour is the agency and only the agency; significance is size (3, 5, 7px radius) and the high-significance glyph inside the point. Dashed heather halos mark lens hits and every other point dims to 35 percent, so a lens reads at a glance without a legend.
- Analysis lane: tried inline "analysis" rows in the event list. Rejected outright: the brief and the Care Inspectorate guide say analysis must never look like a fact. Analysis lives in its own tinted lane as bracketed spans, in its own section under the list, and in the print pack under a separate heading.
- Add event form: one dialog with a radio at the top, "A fact" or "An analysis note", rather than two buttons. The schema enforces the separation: a fact that reads as opinion ("I think", "seems") is rejected with a message that sends the user to an analysis note; an analysis note must link at least one fact.
- Print pack: Chrome does not support `counter(page)` in fixed running elements, so pages are split in JS (18 rows a page) with a header and footer per page carrying the marking, reference, subject and "Page n of m". The classification banner sits above the first page.
- Inbox: laid out as "as received" (raw source fields, in a well) beside "proposed for the chronology" (plain-language title, significance). The human-in-the-loop step is the layout, not a checkbox.

### Self-critique against brief section 8

1. Warmth without decoration: yes. Paper steps and hairlines carry the hierarchy; no shadows except the dialog and the typeahead popover, which float.
2. Accent discipline: heather appears only where the product speaks: primary actions, selected states, focus, the analysis lane, the voice block rule, lens halos. Police blue is never confused with it.
3. Colour never alone: every agency has glyph plus label; significance is size plus a word in the list; risk pills carry an icon and a word; lens hits use a dashed halo plus dimming.
4. Density: the compact toggle now bites on the event list (32px rows) and the sheets. The lanes chart has its own compact prop for the Person record preview.
5. Type: Bricolage only on the name, page titles, clock numerals and the voice quote. Atkinson everywhere else. JetBrains Mono only on audit timestamps.
6. Motion: the lanes settle on first load (320ms, staggered 30ms per lane) and nothing else moves unless the user acts. Reduced motion zeroes it.
7. Copy: buttons say what happens ("Promote to integrated chronology", "Record lawful basis and promote", "Open with a reason"). Empty states say what to do next.
8. What still looks generic: the People list is a plain filter row over a table. It does its job, but it is the one screen a template could produce. Left as is; the drawer affordance on hover is what makes it ours.

## Phase 3

### What was tried and rejected

- Process dashboard frame: the first draft gave each process type its own page layout. Rejected: five layouts meant five places to learn. Every process now shares one frame (reference row, title, subjects, next meeting, stage stepper, clocks, then a two-column body of type-specific panels on the left and participants, views, meetings, sharing and actions on the right). The stepper is the only element that changes shape per type, because the stages differ by statute.
- Stage stepper: tried a horizontal progress bar with percentages. Rejected: statutory stages are not a percentage of anything. The stepper is a list of named stages with the date and the person who moved the process into each one, taken from `stageHistory`, and the ASP stepper hides whichever of support plan and protection plan does not apply.
- Clocks on the dashboard: tried a compact row of numerals only. Rejected: a numeral without its rule is a number without a meaning. Each clock carries the rule label, the trigger, the due date, and where the rule is Local or Verify the confidence and a TODO(verify) marker, the same object as in Admin.
- Views panel: tried tucking the person's views into the participants column as a quote. Rejected: the brief makes the person's views prominent. The views panel sits at the top of the right column on every dashboard, with the advocate, interpreter or carer who recorded them named, and an empty state that says the views have not been sought rather than hiding the panel.
- MARAC perpetrator exclusion: tried an "excluded" pill on the participants list. Rejected as too quiet. The MARAC panel carries a boxed statement naming who must not receive anything about the process, above the DAQ breakdown, and the same exclusion drives the invite and distribution generators in Phase 4.
- MAPPA restricted state: tried a modal that demanded a reason on entry. Rejected: a modal on navigation traps keyboard users and hides the stage the process is at. The restricted state is a page: the process type, stage and lead agency are visible (presence), the reason for restriction is in words, and "Open with a reason" is an ordinary button for Responsible Authority agencies only. The break-glass window is four hours and every read is audited.
- Statutory form dialogs: tried building them as multi-step wizards. Rejected: practitioners fill these forms with the file open beside them, so a wizard hides context. Each form is one dialog with the schema errors inline and the outcome computed live (the DAQ shows the count of yes answers against the threshold; the three-point test shows which limb is unmet).
- LSI workspace: tried one dashboard per resident. Rejected: an LSI is one investigation with strands. The Whinbrae House process has six subjects; the LSI panel lists strands per resident with their own status, the provider dissent is recorded by name, and the setting-level events sit in every resident's chronology.

## Messages (03 Sep 2026): the copy catalogue

- Every string a person can see or hear moved into `packages/messages/src/en-GB.json`, one namespace per feature, with a context file for editors and typed keys generated from the JSON (D-050). Tried and rejected: `next-intl`, because the app is a static export with its own router and one locale, and its routing and server loading have nowhere to go; `react-intl`, because it wraps the same `intl-messageformat` engine without the runtime override layer the Admin editor needs (D-051). ## Person360, classification and the ASP workbook (03 Sep 2026)

- The Government Security Classification went in as a derived value rather than a chosen one. The temptation with a scheme like this is to add a dropdown and a banner across every page; Annex 2 says the opposite, that routine Official needs no marking, and a product that stamps OFFICIAL on everything teaches people to stop reading markings. So `marking()` returns undefined at Official, both components render nothing there, and the only marked state is Official-Sensitive (D-058). Tried and rejected: the existing `ClassificationBanner`, which marked all three levels including Official, was deleted rather than fixed; nothing used it, and it was the wrong idea rather than a wrong implementation.
- Aggregate reports were marked Official-Sensitive and are now Official. A report of counts that names nobody is exactly the routine Official information Annex 2 says not to mark, and the print pack was carrying a marking on every page of it.
- Reclassification lives on the process header beside the restricted indicator, not in Admin. A classification is a fact about one record, and the decision belongs where the record is. Anyone with full access may raise it; lowering needs one of the configured roles and is refused with a toast rather than applied quietly, because the point of deriving the level is that it cannot be talked down. Both are audited as their own acts, and the lower is tinted critical alongside break-glass.
- The Admin markings section stopped being three editable marking texts and became three parts: a read-only table of the derivation rules in the order `classify()` checks them, the handling instructions (a plain-language note plus a set of short instructions appended after the marking), and the roles permitted to lower. The marking text itself is no longer editable, because it is not an area's to choose; `classificationMarkings` lost its `label` field entirely.
- Then the three ASP source documents arrived, and nine field sets turned out to be wrong. Every one had been reconstructed from the 2024-25 technical report's glossary, which does not print the lists. Reading them from the workbook itself changed harm types (11 to 12, hoarding split out), client groups (10 to 11, infirmity or frailty added), age bands (an invented 8 to the workbook's 12), ethnicity (one "not collected" line to 8 census categories), gender wording, location of harm (a 3-value guess from the adult's address to an 11-value recorded field), referral source (11 agencies to 33 sources), and LSI service type. Tried and rejected: keeping the derived location of harm as a fallback where the field is unset, because a national return that quietly guesses is worse than one that says "Not known".
- The expected labels for the field set test went into a JSON transcription fixture rather than the test file. Three reasons: the workbook's own em dashes then sit in data rather than in code, where the checkers can leave them alone without a new exception; the seven labels the product deliberately adjusts are named in one list beside the reason; and the next edition of the workbook is a readable diff of one file. The em dash checker gained a second, explicitly listed exception for transcriptions.
- The export writes into the published workbook rather than producing a spreadsheet of our own. Tried and rejected: generating a fresh .xlsx with the same figures, because the return is a specific file with charts, validation and helper tables that Scottish Government expects, and a lookalike would be rejected. The consequence is that the template has to be chosen from disk, which is also the honest arrangement: it is published annually, and a copy inside the build would go stale silently.
- The formula guard is the part worth keeping. Every Total row is a SUM, and a literal on top of one produces a workbook that looks correct and stops adding up as soon as anyone edits it. `nmdsCellMap` never emits those cells, and `fillWorkbook` re-checks the actual template before writing each one, returning refusals rather than throwing so a new edition appears as a list on screen (D-060).
- The cell map test reads the workbook with a small zip and XML reader rather than ExcelJS. A test that used the same library as the writer would pass on a bug in that library, and the domain package has no runtime dependencies worth losing.
- Axe caught a real defect during the export work: the hidden file input driving the "Choose the blank workbook" button had no label. It is labelled and out of the tab order now. That is the gate doing its job rather than a formality.
- The screen is a preview first and a download second. The workbook's own guidance puts data quality on the person submitting, so every figure appears against the cell it will be written to, the workbook's check rows run before a file exists, and the caveat lines are drafted from what the product knows it cannot count. Leaving those boxes blank is what makes a nought look like a measurement.


## Cryptographic architecture (03 Sep 2026)

- The instruction was "ensure that everything is end-to-end encrypted", and the first hour went on not building it. Taken literally it cannot be met by a product whose controller has to answer a sheriff's order, and the ICO's own encryption guidance treats data made inaccessible by encryption as a likely failure of Article 32 in its own right. The reframing that survived is one sentence: the product does not encrypt everything to one key, it encrypts every record to exactly the set of people entitled to see it. That is written down in three places before any code was written, because the risk with a requirement like this is not that the maths is wrong, it is that a demo says something the maths does not support.
- The threat model was written first and the adversaries were ranked by how often they actually occur rather than by how dramatic they sound. The curious colleague looking up a neighbour is first. That ordering did more to shape the design than any algorithm choice: it is what turned "encrypt the database" into "wrap each content key to the entitled principals", because the naive version defends against a stolen backup and does nothing at all about the breach that ends careers in this sector.
- Two adversaries are marked partial defence and the wording was left blunt. A compromised practitioner account sees what that practitioner sees, and two colluding escrow holders can read anything. Tried and rejected: softening either into "mitigated by audit and governance", because a reviewer who finds the hedge stops believing the rest of the document.
- `canSee` was deleted rather than deprecated. A deprecated boolean is a boolean somebody calls at half past four on a Friday. What replaced it, `accessRank`, orders levels for display and carries a comment saying it must never gate content, and the comment is backed by a test that reads every `.ts` and `.tsx` in `apps/web` and `packages/domain`, strips comments and fails on a call to `canRead(` or `canSee(`. Stripping the comments was not optional: the first version of the test failed on its own explanatory prose.
- Presence readers are deliberately not wrapped and escrow always is. Both were close calls that went the way that costs more. Wrapping presence readers would have made one screen simpler and would have handed them the content. Leaving escrow off some records would have read better in the threat model and would have meant a record the controller could not produce on a court order.
- The "What the host can see" screen shows the real metadata, in full, including classification and every key holder's opaque identifier. Tried and rejected: a version showing only ciphertext, which is the version that demos better and is a lie. The one person in the room who knows it is a lie is the security reviewer, and they are the person the screen exists for.
- The audit chain verification screen has a second button that verifies a deliberately tampered copy, edited the way somebody covering their tracks would edit it, by turning a restricted read into an ordinary one. A verification screen that has only ever said "verified" proves nothing, and the same reasoning put a tampered fixture in the unit tests.
- `escrowDecision` refuses two holders from the same organisation. That could have been a line in a policy document and a note in the DPIA. It is in code because policy is not what runs at two in the morning, and because a refusal a reviewer can trigger in the demo is worth more than a paragraph they have to believe.
- Rotation returns `priorAccessRemains: true` and the field is not decoration: it drives the sentence shown when a chair removes someone from a case. Removal stops future access and cannot unread what was already read. A chair who believes otherwise makes a different decision, so the copy says it in those words and nothing softens it.
- Argon2, not PBKDF2, and the lint rule refuses both PBKDF2 and scrypt anywhere in the repository, including for a cache key. Same reasoning as MD5: a reviewer grepping a safeguarding product for a broken primitive will not stop to read what it was used for.
- Three real defects the gate caught rather than a person. Axe found `ClassificationMarking` rendering `role="note"` with no accessible name, and the hidden file input on the workbook export screen with no label. The new weak-crypto rule found a `Math.random` in the toast component, which was replaced by a module counter that is better anyway because it is unique by construction rather than probably unique; the explanatory comment then tripped the same rule and had to be reworded, which is the rule working as intended.
- The React Compiler refused the memoised vault built outside the component, so it moved into the Zustand store as state. Then routing persistence through `sealLocal` broke every Playwright spec at once, because the sign-in helper writes a plaintext session. A bounded and documented upgrade path reads a plaintext session once and immediately re-seals it, which is also what a real deployment would need on the day the encryption ships.
- The demo gained a beat rather than a paragraph: the host view sits immediately after the restricted MAPPA moment, because the question "would it refuse the people running the servers" is the one the room is already thinking when they have just watched need-to-know refuse a social worker.

## Dialogs, and what a geometric test finds (03 Sep 2026)

- The reported bug was that every modal rendered pinned to the top left, over the chrome, and that tall dialogs clipped so the primary action could not be reached. The first hour went on the wrong file. `base.css` was the obvious suspect and it was innocent; reading the computed styles in a real browser gave `margin: 0px; position: absolute; inset: auto 0px auto 0px`, and grepping the compiled stylesheet found the author: Tailwind's preflight, `*,::after,::before,::backdrop { margin: 0 }`. A native dialog centres by resolving `auto` margins against its two zero insets, so zeroing the margin is enough to un-centre every dialog in a product without touching one line of its own CSS. The lesson worth keeping is that the search should have started at the compiled output, because that is the only place where the framework's opinions and ours are both visible.
- So the guard reads the compiled output too. A Stylelint rule on the source would not have caught this, because the source never set a margin. `tooling/dialog-margin-guard.mjs` reads `apps/web/out` after a build and asserts a rule sets `position: fixed`, `inset: 0` and `margin: auto` together. It exits cleanly with a message when there is no build to read, so it does not fail a fresh checkout.
- The regression spec earned its place twice before it ever ran green. It caught an infinite render loop in the new primitive, where the scroll-shadow `setState` built a fresh object on every scroll frame and `children` was in the effect's dependencies, which made a click on the trigger never resolve. Then it caught a worse one: `display: grid` set unconditionally on `.dialog` overrides the user agent's `dialog:not([open]) { display: none }`, so every closed dialog stayed as a full-viewport `position: fixed; inset: 0` box quietly swallowing clicks meant for the page behind it. Diagnosed with `document.elementFromPoint` over the trigger, which returned the dialog at 1440 and the button at 1920 because the layouts differ. Both bugs were mine, both were invisible to every other test, and both were found by assertions about geometry rather than about behaviour.
- Nothing in the spec skips. The first version used `test.skip` when a trigger could not be found, which turned four unreachable dialogs into passes and read as a green suite covering six dialogs when it covered two. A missing trigger is now a failure with a message saying which dialog is unreachable, and finding the real triggers turned up two absences worth recording rather than working around.
- The first absence: `informationRequests` is seeded empty, so the "Respond" dialog on Sharing has no data behind it and cannot be reached by any persona. The screen renders its empty state correctly and the dialog is unreachable code today. Left out of the spec deliberately rather than quietly, and it belongs to the two-way connector work, which is what will put a request in the inbox.
- The second: no social work connector events are pending in the seed. Health has six, education two, police two, and social work none, so a social worker who pulls from ECLIPSE gets "ok" and an empty inbox. The spec uses a health persona. This is honest as far as it goes, since the demo path pulls as health, but a social worker pulling and finding nothing is a bad first minute of a demonstration.
- Tried and rejected on the scroll lock: releasing it from the element's own `close` event, which is where it started. That handles the ways a dialog shuts and not the way it disappears. Navigate away with a modal open and the component unmounts without firing `close`, the count never comes back down, and the page stays unscrollable for the rest of the session with no element left to blame. Pairing the lock with React's effect cleanup handles both, and there is a unit test that unmounts an open dialog and asserts the page scrolls again.
- Tried and rejected on the contact sheet: raising the thumbnail and keeping the second encoding. Measured at 720px it came to 15.3 MB against a 16 MB budget, and at 800px it came to 16.2 MB, so the legible version of the two-copy design does not fit. The two-copy design was the problem, not the thumbnail size.

## Layout modes, and the difference between collapsed and clipped (03 Sep 2026)

- The reported symptom was a list: the rail crushed rather than collapsed, the top bar overlapping it, the drawer holding 360px, the stepper clipping, the rail footer orphaned. Measuring first turned five symptoms into one cause. A probe at eight widths gave `railScroll {sw: 125, cw: 71}` at 1100px, which says it plainly: the rail wanted 125px, was given 71, and nothing collapsed. The grid column came from a media query and the rail's own state came from the appearance store, so the two were free to disagree. Everything else on the list was the same disagreement wearing different clothes.
- Which is why the fix is one attribute rather than five patches. The stylesheet now has no media query for layout at all. That was worth doing on its own: the old file had the 1279 boundary written three times in three selectors and the 1023 boundary once more, and getting them to agree by hand is exactly the maintenance nobody does.
- The first version of the mode effect was React error 185 at every width above 1024, and the mistake is worth writing down because it is easy to repeat. `useChrome()` with no selector returns the whole Zustand store object, which is replaced on every write, so an effect that depends on it re-runs after its own `set`. The page was blank at 1440 and correct at 900, which read like a layout bug and was a state bug.
- Tried and rejected: making the drawer narrower below 1280 and keeping it docked. At 1024 a 240px drawer still leaves the record 700px and the drawer itself too narrow to hold the need-to-know table without wrapping every row. An overlay is the honest answer, and it costs nothing to build because the dialog primitive from the previous round already had the top layer, the focus trap, Escape and the scroll lock.
- The 400 percent zoom work found three things that had nothing to do with the chrome. The top bar could not wrap and held 592px of content in a 320px window. The chronology row has a real 1270px minimum across nine columns, and its viewport scrolled vertically only, so the row overflowed the page instead of the list. And the process record's full-width row had the default `min-width: auto`, so its min-content set the grid track for the two columns above it: the container query was collapsing the layout correctly and the single column was still 453px wide. That third one is the kind of bug that survives review, because every rule involved looks right on its own.
- The truncation policy came out of writing the assertion rather than the other way round. The first version failed on the rail labels in the icon state, which are visually hidden with a 1px clipped box and therefore satisfy `scrollWidth > clientWidth` trivially. Excluding boxes of 2px or less is not a fudge: visually hidden text is not truncated text, and an assertion that cannot tell them apart is measuring the wrong thing.

## Links, and the difference between refusing and hiding (04 Sep 2026)

- The rule that took the longest to be sure about is the one that sounds wrong at first: a link the reader cannot follow must look exactly like one they can. Every instinct says grey it out. But a greyed link is an answer to a question the reader never asked, delivered without an audit entry, and repeated across a screen it draws a map of what is hidden. The version that refuses in writing, on a screen, and records the attempt is the one an inspector can review afterwards. The spec asserts the sameness rather than the difference, which felt backwards to write and is the point.
- The exclusion rule found a real bug the moment it was enforced centrally. The MARAC referral panel had been rendering "Perpetrator: Ryan Kerr" as a link into his record, immediately beside a pill reading "Must not receive anything about this process". Both halves were written deliberately and neither author saw the other. That is the argument for a rule living in one component rather than in a convention.
- Which then exposed that the rule had nowhere to fire. `PersonLink` with a case in scope was only ever used on subjects, and a subject is never an excluded party, so the branch was unreachable code by the audit's own standard. The fix was not to delete it but to notice why: the product had no screen listing who a case is about. It has one now, and the rule is exercised by the demo path rather than by a test written to reach it.
- Tried and rejected: opening the timescale rule from an effect when the address carries `?rule=`. It worked, the lint rule caught it, and the lint rule was right for a reason beyond the extra render: state copied from the address on mount stops agreeing with the address the moment anyone presses back. Deriving the open rule from the query and clearing the query on close is both smaller and correct.
- The recently-viewed test failed first because it navigated with `page.goto`, which is a full page load, which is a new session, which empties a store that is deliberately not persisted. The test was wrong and the behaviour was right; the fix was to click through the product the way a person would, which is a better test anyway.

## Critique of the sign-in screen, before rebuilding it (04 Sep 2026)

Written first, against the committed screenshot, because a rebuild without a written account of what was wrong is a redecoration.

- **It is two panes that stop, not a composition.** The left surface ends at 597px and the right is a bare field with cards on it. Nothing crosses the join and nothing ties the halves together, so it reads as a marketing page and an application put side by side rather than one screen.
- **Four hundred pixels of nothing.** Between the three badges and the demo note at the bottom of the left pane there is a void, and the eye has no reason to travel down into it. The one thing in that corner is the most important sentence on the screen.
- **The strongest statement is in the smallest type in the least looked at place.** "This is a demonstration build. Every person, case, address and number is synthetic" is the honest thing this screen has to say and it is a footnote. It should be the second thing read, not the last.
- **Thirteen organisation cards, all the same weight.** The demo uses five of them. A three across grid of thirteen equal cards makes the first decision the largest one on the screen, and it is the least interesting decision anybody makes here: nobody watching cares which of thirteen organisations was clicked, they care who you are.
- **The step numbers promise a stepper that does not exist.** "1 Your organisation" with "2 Who are you today" appearing only after the first is answered. A numbered step hidden until its predecessor completes is progressive disclosure, and numbering it claims a progress indicator the screen has not got.
- **Choosing an organisation scrolls the personas below the fold.** At 900px the thirteen cards fill the pane, so answering step one moves the thing you now have to read out of sight. On a projector that is a scroll in the first ten seconds of a demonstration.
- **The type is from a different product.** A 3rem display headline in front of an application whose base size is 0.875rem. The headline is a good line and it is set as though the next screen were a landing page.
- **The remembered persona is remembered and then hidden.** `mas.lastPersona` is written on sign-in and read on arrival, and the "Last time" tag it drives only appears after the organisation has been chosen. The one person who most wants to get straight in, the person demonstrating it for the fourth time, still makes both choices.
- **Keyboard-possible, not keyboard-first.** Nothing takes focus on arrival, there is no type-ahead, and the fastest keyboard route to a persona is thirteen tabs and then up to a dozen more. The brief asks for keyboard-first and this is the version you get when you only check that tab reaches everything.

What is right and stays: no credential field, because a password box that accepts anything is a lie told in the first five seconds; the persona blurbs, which are genuinely useful when choosing who to be; and the fact that the choice is presented as a choice rather than dressed up as authentication.

## The write pipeline (04 Sep 2026)

- The near-match test failed first and the test was wrong in an interesting way. `nearMatchesOnRegister` only compares against register entries that hold a name somebody typed, and the seeded MARAC register holds Ryan by `personId`. So a resembling name produces no warning there, and the exact check by id is the only one that fires. ## Creating a person, which begins with looking for them (04 Sep 2026)

- The design question was where the create button goes, and the answer turned out to be that it does not exist until the search has been reviewed. Putting a search *beside* a create button is what most systems do and it is why they hold duplicates: on a Friday afternoon with a child in front of you, the button that makes the record you need is the one you press. So the sequence is the door, and the dialog is a sequence rather than a form. Nothing is replaced as it advances, either: the search stays on screen while the candidates are read, and the candidates stay on screen while the details are typed, because a practitioner who has just asserted that none of five is the person should be able to see the five while they type the sixth.
- Writing the matcher first and the screen second was the right order and made the screen almost fall out. `findDuplicateCandidates` returns *reasons*, not a score, and once the reasons existed the candidate row designed itself: name, date of birth, and a row of chips saying why this one came back. A percentage would have been half the work and would have asked the reader to trust a number they cannot check.
- The surname-only search broke three tests at once and the cause was one line. `nameSimilarity('Boyle', 'Aiden Boyle')` fails every branch it has, because it compares whole names, and a search with only a family name in it is the commonest search there is. The fix compares the query's parts against the person's parts. Worth recording because the failing tests all looked like different bugs.
- Dropping an address-only match was not obvious until the seed made it obvious. Whinbrae House has eleven residents and a refuge would have more, so an address match with nothing else behind it returns the building rather than the person. It is still a strong reason when it accompanies a name or a date, which is where it earns its weight.
- Tried and rejected: showing only the candidates the reader can open. It is the tidier list and it is exactly backwards. The invisible record is the one that produces the duplicate, so it is now the loudest row in the list, with a dashed edge, a plain sentence and a route to asking for access.
- The gate came out of writing the refusal copy rather than the code. "Your role reads across cases for oversight and does not hold them" is a sentence somebody can act on; a disabled Save button at the foot of a form they have already filled in is not, and it wastes their afternoon first.
- The lint gate had been red since the sign-in rewrite and nobody noticed, because `pnpm typecheck` and `pnpm test` were green and the eye stops there. Eighteen orphaned message keys and three namespaces the checker did not know about. Fixed here rather than left for the tidy-up commit, along with a false positive of my own making: the dialog margin guard matched the word "dialog" anywhere in a selector, so a paragraph in `AddPersonDialog.module.css` resetting its own margin failed it. A guard that cries wolf is a guard people run with their eyes shut.

## Merge, and the discipline of making it reversible (04 Sep 2026)

- Writing the unmerge first would have been better and I did not. Writing the merge first led me towards a field-by-field union that I then could not invert: given a survivor and a retired record that both held the same CHI number, nothing afterwards can say which one the survivor's copy came from. Keeping both records whole on the merge record makes the question unnecessary, and it is less code.
- The walk beat the list, decisively. A hand-written list of the places a person id appears got to fourteen before I stopped writing it and started counting: the seed holds twenty-six references to Aiden Boyle outside the audit ledger, several of them in `detail.referral.childPersonIds` and similar places nobody would enumerate correctly twice. The generic walk is eleven lines, it records what it did, and the test asserts that nothing but the ledger still names the retired record.
- The identity-preserving return was not premature. It started as tidiness, then turned out to be what makes persistence tractable: the overlay is a per-record patch, so "which records actually changed" has to be answerable, and object identity answers it exactly where a deep comparison would be slow and a blanket rewrite would put the entire dataset into local storage.
- The consequences panel went through three drafts. The first was a warning triangle and "this cannot be undone", which is false here. The second said "this affects many records", which is true and useless. The third counts them, because a number a practitioner can compare against what they expect is the only version that is worth reading.
- Tried and rejected: offering the merge from the People list with two checkboxes. It reads as a bulk operation, and this is the least bulk operation in the product. It belongs on the record, under the process badges, away from the person's name.

## Household and network, and the bug that hid behind a dialog (04 Sep 2026)

- Splitting household from network took one afternoon of reading the scenarios and about twenty lines of code. Marion Fraser's nephew is network; Kayleigh Docherty's children are both; Derek Muir's household is a supported tenancy with one person in it. Once the two lists exist separately, every one of those reads correctly with no special cases, which is the usual sign that the distinction was real rather than imposed.
- Dating the memberships was the change I nearly did not make. `memberIds: string[]` was already there and adding a parallel `pastMembers` would have been half the work. It would also have been two answers to one question within a week. The migration touched fourteen call sites, all but two of them seed writers, and the generator now derives each member's start date from the person's own address history so the household and the address history cannot disagree.
- Three e2e tests failed identically: press the button, the dialog stays open, nothing on screen says why. That is the worst failure shape a form can have, and it took a console capture to find: the write pipeline was reading `record.classification.handling` on a household, which has no classification, and the exception took the handler down before the dialog could close. The lesson is not about classification. It is that a `as ClassifiedRecord` cast in a pipeline that runs for every collection is a claim nobody checked, and the pipeline is exactly the wrong place for one.
- The second bug was invisible for the opposite reason: everything looked right. The "Add someone to the household" button could not be clicked because the sheet head beside it had overflowed its own sheet and was drawn on top. `flex-shrink: 0` on the actions with no `flex-wrap` on the head, in a 280px column. Playwright found it because a click is a spatial assertion and a screenshot is not.
- Ending a relationship "today" left it in the live list, which read as the button not working. The domain was right: `covers` includes the day a period ends, because a person did live there that day. The list is asking a different question, so it asks it differently now, and both meanings are pinned by tests.
- The design point I keep coming back to: "this will exclude Marion Fraser from the MARAC" is worth more than any number of warning triangles, and it costs nothing to compute because the rules are already there. Running the real register twice and diffing is eleven lines, and it means the sentence on screen cannot drift from what the product will actually do.
- One more from this round, and it is a general one: a closed dialog left in the markup is not free. The person record hosts three person pickers, each of which carried a whole create flow, so the record shipped three hidden copies of it with the same test ids and the same controls in each. Mounting them only while open removed the duplication and about two thirds of that subtree.

## Two gates, and reading the clock rules instead of assuming (04 Sep 2026)

- The task said opening a child protection investigation starts `cp.cppm.initial`, and I nearly wired it to the concern. Reading the rule's own trigger text stopped it: the clock runs from the investigation beginning at the IRD, not from the concern being recorded. Doing the same for every other opening changed most of the answers. A MARAC referral starts no clock at all; both MARAC clocks run from the case being heard. So the dialog now says "No statutory clock starts here" and then says what will start one, because a practitioner who expects a countdown and sees none needs to know whether the product forgot or the law simply has not started counting yet.
- Keeping eligibility and permission apart was worth the extra type. On the same 16 year old, read by a children and families social worker, adult support and protection is eligible and not hers to open, and those are different sentences with different routes out. A single "not available" would have been half the size and would have taught nothing.
- MAPPA was the one I expected to get wrong and checked twice. Annex 3 Table 6 has an Under 18 band, so an age floor would be a bug that a coordinator spots immediately. It warns instead, and names the Act that changes how the case is run.
- The seed could not show the most interesting case in the step. A uniform draw of children from 0 to 17 across 58 households produced no 16 or 17 year olds at all, which is chance rather than a bug and still a gap: the product handled the case and had nobody to demonstrate it on. Every fourth family household now has one deliberately.
- Tried and rejected: filling an opening's unknown fields with plausible defaults. An ASP concern needs a referral source and a location of harm before it validates, and "own home" would have been right most of the time and a fabricated figure in a national return the rest. They open as "other" and "not known", which is the answer the workbook itself provides for exactly this.

## The rest of the create paths, and a global action that is not a shortcut (04 Sep 2026)

- The audit of what already had a create path was the useful part of this step. Chronology events, views records, actions, meetings, shares, information requests, three of the risk assessments and connector promotion were all covered. Missing: plans, alerts, ASP protection orders, MAPPA disclosures, AWI supervision visits and investigations, manual register entries, and the global action itself. Building the six first meant the global action was genuinely complete when it landed rather than being a menu with three live entries.
- Entering a plan as outcome rows rather than a text area changed the feel of the whole dialog. The first version had a single "outcomes" textarea and a note asking for one per line. It looked tidier and it was wrong: an action points at an outcome, so an outcome needs an id, and parsing ids out of a text area on save is a way to lose them the first time somebody reorders their lines.
- The protection order preview earns its space. Showing "Removal order valid until 11 Sep 2026" and "removal must take place by 08 Sep 2026" before the button is pressed is the difference between a clock and a countdown somebody knew about. It is computed by running the real rules, not by rendering a sentence, so it cannot drift from what the write records.
- Tried and rejected: a disclosure dialog that also recorded the decision. It would have been one form instead of two steps, and it would have made the register a list of things one person did rather than a record of decisions somebody with the authority made. The dialog now says, in the dialog, that the record opens pending.
- The global create action nearly became a second implementation. The first sketch had it navigate to the right screen with a query parameter that the screen would notice and open its dialog. That is a lot of wiring, and it means the menu and the screen can disagree. Mounting the same dialog component from the menu is smaller and cannot drift, and it made "which of these are not dialogs" an honest question with a visible answer: a meeting, an action and a share are made on their own screens and the menu says so.
- The bug worth remembering: the create menu cleared its chosen person in `onClose`, and the dialog primitive fires `onClose` for the programmatic close that hands the create over, so the alert dialog opened with no person and rendered nothing at all. Clearing on open instead is one line different and correct for a second reason, since the menu should start fresh anyway.
- One existing test broke, and it was the test. `getByText(/need-to-know/i).first()` in the meetings spec started matching a hidden line of copy in the create menu, which now sits in the DOM of every screen because the top bar mounts it. The assertion meant "the generated invitees carry the rule that put them there", so it now says that, matching the rule reference. A loose regex over the whole page was always going to break on the day somebody added copy to the shell.
